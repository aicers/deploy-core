# Image archive fixtures

Each fixture here is an image archive, `<name>.tar`, with the declaration it
is classified against, `<name>.declaration.json`. A declaration is the serde
form a package manifest uses for `PayloadArtifact.image`. Every archive is a
few kilobytes.

`inventory.json` is the authority on every fixture: its kind, its file names,
the archive's SHA-256, its expected verdict and its provenance. This file
explains how to read it. Archives built while a test runs — at the limit
boundaries, for I/O faults or for the worst case — are never checked in and
never recorded here.

## Kinds

- **`synthetic`** — generated by exactly one reproducible generator in this
  repository, named in `provenance.generator`, from the parameters in
  `provenance.parameters`. The test named in `provenance.test` regenerates the
  archive byte for byte and fails if the checked-in file differs.
  - `builder` — the public `image::test_support::SyntheticImageArchiveBuilder`.
    Regenerated through the public API by
    `tests/image_fixture_inventory.rs::builder_fixtures_regenerate_byte_for_byte`.
  - `raw-generator` — the crate-private, test-only raw generator in
    `src/image/test_support/raw.rs`, which starts from a builder archive
    described by `parameters.base` and reshapes it into the form named by
    `parameters.form`. Regenerated by the unit test
    `src/image/test_support/tests.rs::raw_generator_fixtures_regenerate_byte_for_byte`.
- **`docker-capture`** — raw `docker save` output from a disposable Docker
  engine. It has no generator and is never regenerated: its bytes are
  immutable, it is checked only by its recorded SHA-256 and verdict, and it
  carries none of the determinism or content promises synthetic fixtures do.
  Its provenance is the manual capture record: `engine_version`,
  `store_mode`, `architecture`, the exact `command`, the
  `source_image_digest`, and the `declaration_derivation` that
  `docs/image-archive-interoperability.md` describes. Replacing a capture
  means making a new capture with new provenance.

## Verdicts

`verdict` is what `image::test_support::check_image_archive` returns for the
archive against its declaration, with the archive's file name passed as
`archive_path`:

- `"accepted"` — the archive is accepted;
- `{"error": "<variant>", "detail": "<Debug>"}` — the archive is refused with
  the `ImageVerifyError` variant `<variant>`, and `<detail>` is the `Debug`
  form of its `feature` (for `UnsupportedArchive`) or `reason` (for
  `InvalidArchive`), exactly as the validator reports it. `archive_path` is
  not part of the verdict.

A refused fixture's verdict is whatever the validator returns for it. During
the raw walk of the image tar the validator reports the first offending entry
in archive order; after the walk, each phase reports in its fixed check order.
A layout that lacks a required entry, such as the compatibility
`manifest.json`, is malformed input and so `InvalidArchive`, not a named
exclusion.

## Fixtures

Accepted, from the builder:

- `uncompressed`, `gzip`, `multi-tag` and `scratch`;
- `repeated-layer`, with one blob at positions 0 and 2;
- `explicit-variant`, `arm64` with `v8`.

Accepted, from the raw generator:

- `layer-sources`: the `gzip` archive plus a complete, consistent
  `LayerSources`.

Refused, from the raw generator:

- `classic-layout`: `<id>/layer.tar`, `<id>/json`, `<id>/VERSION`,
  `<hex>.json` and `repositories` — `UnsupportedArchive`, `LegacyExportFile`;
- `graphdriver-extras`: a supported archive plus `repositories` and an
  unreferenced V1 config blob — `UnsupportedArchive`, `LegacyExportFile`;
- `containerd-nested-index`: a nested index with an attestation manifest and
  extra descriptor annotations — `UnsupportedArchive`, `NestedIndex`;
- `oci-without-compat-manifest`: `oci-layout`, `index.json` and the
  referenced blobs only — `InvalidArchive`,
  `MissingLayoutFile { file: CompatibilityManifest }`;
- `multi-platform-index`: two manifests, for `amd64` and `arm64`/`v8` —
  `UnsupportedArchive`, `MultipleImages`;
- `zstd-layer`: a layer re-stored as a zstd frame under the zstd media type —
  `UnsupportedArchive`, `LayerMediaType { position: 0 }`.

## Regenerating synthetic fixtures

Synthetic output depends on the `tar`, `flate2` and `miniz_oxide` versions the
build resolves. A dependency update that changes the bytes fails the
regeneration tests, and the fixtures are regenerated in the same change:

```sh
cargo test --lib -- --ignored write_synthetic_fixtures
```

That ignored unit test rewrites every `synthetic` archive and declaration from
its recorded parameters, and records each one's SHA-256 and verdict in
`inventory.json`. Review the diff: a verdict that moves is a change in what the
validator decides, not a formatting detail. `docker-capture` fixtures are
never touched.

To add a synthetic fixture, add its record with its parameters to
`inventory.json`, run the command above, and check the result in.

## Docker captures

No disposable Docker engine was available when these fixtures were made, so no
real `docker save` capture is checked in. The evidence is reported as not
run, never mocked:

- `graphdriver-store` `docker save` capture: **not run**
- `containerd-store` `docker save` capture: **not run**

When a disposable engine is available, capture a tiny `FROM scratch` image
from each store as `docs/image-archive-interoperability.md` describes, add
each as a `docker-capture` fixture with its full capture record and the
verdict the validator reports for it, and remove its line above.
